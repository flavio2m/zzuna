# UI

## Antes de implementar

Sempre verificar componentes compartilhados em:

```text
lib/ui/shared/
```

Ordem de consulta:

```text
Buttons e ações clicáveis
→ lib/ui/shared/widgets/buttons/

Cards
→ lib/ui/shared/widgets/cards/

Campos de entrada
→ lib/ui/shared/widgets/forms/

Feedback visual (SnackBar, Dialog, etc.)
→ lib/ui/shared/feedback/
```

Reutilizar componentes existentes sempre que possível.

Não criar novos componentes quando já existir uma implementação equivalente em `ui/shared`.

### Campos de entrada

Utilizar componentes compartilhados da pasta:

```text
lib/ui/shared/widgets/forms/
```

Evitar uso direto de:

```dart
TextField
TextFormField
```

quando existir um componente compartilhado equivalente.

Não utilizar SizedBox ou Divider diretamente.

Utilizar:

```text
AppSpacing
AppDivider
```

para manter os espaçamentos padronizados.

### Objetivo

Garantir:

* Consistência visual
* Reutilização de código
* Centralização de manutenção
* Padronização da experiência do usuário

---

## Quando criar Page

Criar Page quando a funcionalidade representar uma tela completa.

Exemplos:

```text
login_page.dart
home_page.dart
profile_page.dart
```

Estrutura:

```text
ui/[domain]/[feature]/
├── [feature]_page.dart
└── viewmodels/
    └── [feature]_viewmodel.dart
```

### CRUD Simples

Para CRUDs simples:

* Poucos campos
* Sem múltiplas etapas
* Sem fluxo complexo
* Sem múltiplas seções

Preferir:

```text
ListPage
+
CreateModal
+
UpdateModal
```

Não criar:

```text
CreatePage
UpdatePage
```

para CRUDs simples.

Exemplos comuns:

```text
Conta
Cartão
Categoria
Banco
Fornecedor
Centro de Custo
```

CRUDs complexos devem ser avaliados individualmente.

---

## Quando criar Widget

Criar Widget quando a funcionalidade for reutilizável.

Exemplos:

```text
logout_button.dart
user_avatar.dart
product_card.dart
```

Estrutura:

```text
ui/[domain]/[feature]/
├── viewmodels/
│   └── [feature]_viewmodel.dart
└── widgets/
    └── [widget].dart
```

# Telas de Listagem (CRUD)

## Quando criar

Criar uma tela de listagem quando a funcionalidade possuir:

* Consulta de registros
* Filtros
* Ordenação
* Paginação (quando necessário)
* Ações de editar
* Ações de excluir

Estrutura recomendada:

```text
ui/[domain]/list/
├── [domain]_list_page.dart
├── viewmodels/
│   └── [domain]_list_viewmodel.dart
└── widgets/
    ├── [domain]_filter_bar.dart
    ├── [domain]_list_view.dart
    └── [domain]_list_item.dart
```

Exemplo:

```text
ui/conta/list/

├── conta_list_page.dart

├── viewmodels/
│   └── conta_list_viewmodel.dart

└── widgets/
    ├── conta_filter_bar.dart
    ├── conta_list_view.dart
    └── conta_list_item.dart
```

---

## Organização visual

Sempre que possível dividir a tela em:

```text
FilterBar
↓
ListView
```

Exemplo:

```text
ContaListPage

├── ContaFilterBar
└── ContaListView
```

Objetivo:

* Separar filtros da listagem
* Facilitar manutenção
* Facilitar reutilização

---

## Responsabilidades da ListViewModel

A ViewModel da listagem é responsável por:

* Carregar registros
* Aplicar filtros
* Atualizar resultados
* Escutar alterações do Repository
* Expor Commands para a UI

Não deve:

* Navegar
* Exibir SnackBars
* Manipular Widgets
* Utilizar BuildContext

---

## Filtros

Filtros devem ser agrupados em um DTO.

Criar DTO específico para filtros.

Exemplo:

```dart
class ContaFilterDto {
  String descricao;

  String? bancoSigla;

  bool? ativo;

  ContaFilterDto({
    this.descricao = '',
    this.bancoSigla,
    this.ativo,
  });
}
```

Não passar múltiplos parâmetros isolados para Commands.

Evitar:

```dart
filterCommand.execute(
  descricao,
  banco,
  ativo,
);
```

Preferir:

```dart
filterCommand.execute(
  filtro,
);
```

---

## Atualização automática da listagem

Quando o Repository possuir:

```dart
observer()
```

a ViewModel deve escutar alterações e atualizar a listagem.

Exemplo:

```dart
_repository.observer().listen((_) {
  loadCommand.execute();
});
```

Objetivo:

* Atualizar automaticamente após Create
* Atualizar automaticamente após Update
* Atualizar automaticamente após Delete

Sem necessidade de refresh manual.

---

## Ações de linha

Ações da tabela/lista devem representar apenas operações do registro.

Exemplos:

```text
Editar
Excluir
```

A navegação deve ocorrer na Page.

A ViewModel deve apenas executar Commands.

### Exclusão

Toda exclusão deve solicitar confirmação do usuário.

Utilizar:

```text
ui/shared/feedback/app_dialog.dart
```

Fluxo:

```text
Usuário clica Excluir
↓
Confirmação
↓
Command de exclusão
↓
Feedback
```

Nunca executar exclusão diretamente ao clicar.

---

### Cadastro e edição

Para CRUDs simples:

* Cadastro deve ser realizado em Modal
* Edição deve ser realizada em Modal

Utilizar:

```dart
showDialog(...)
```

com:

```dart
AppFormType.modal
```

## EntityDetails em listagens

Quando a listagem precisar exibir informações enriquecidas:

```text
Conta + Banco
Conta + Indicadores
Conta + Formatações
Cartão + Bandeira
Categoria + Hierarquia
```

utilizar:

```dart
ContaDetails
CartaoDetails
CategoriaDetails
```

Se os dados vierem de apenas um Repository e o processamento for simples:

```text
Entity → EntityDetails
```

a conversão pode ocorrer diretamente na ViewModel.

Não criar UseCase apenas para montar objetos ricos simples.

Antes de criar um UseCase verificar:

```text
05_DOMAIN_USECASE.md
```

---

## Regras

* Toda ação deve passar por ViewModel
* Nunca acessar Repository diretamente da UI
* Nunca acessar Service diretamente da UI
* Utilizar Providers para obter ViewModels
* Utilizar Commands para ações assíncronas
* Utilizar AppSnackBar para feedback
* Utilizar CommandStateExtension para tratar sucesso e erro
* Utilizar DTOs para armazenar dados de formulários
* Utilizar DTOs para filtros
* Utilizar Validators para validar formulários
* O botão da ação principal deve permanecer desabilitado enquanto o formulário for inválido
* Campos com validação devem utilizar AppTextFormField dentro de AppForm
* AppTextField deve ser utilizado apenas para entradas sem validação

---

## Obter ViewModel

### build()

```dart
final viewModel =
    ref.watch(exampleViewModelProvider);
```

### initState()

```dart
final viewModel =
    ref.read(exampleViewModelProvider);
```

## Formulários

### DTO + Validator

```dart
final validator =
    RegisterUserDtoValidator();

final dto =
    RegisterUserDto(
      name: '',
      email: '',
      password: '',
    );
```

---

### Atualização dos campos

Os campos devem atualizar o DTO e reavaliar o formulário.

```dart
TextFormField(
  autovalidateMode:
      AutovalidateMode.onUserInteraction,
  onChanged: (value) {
    dto.setName(value);
    setState(() {});
  },
  validator:
      validator.byField(dto, 'name'),
)
```

---

### Controle de submissão

Criar um getter para verificar se o formulário é válido.

```dart
bool get _canSubmit {
  return validator
      .validate(dto)
      .isValid;
}
```

---

### Execução da ação

Sempre validar antes de executar o Command.

```dart
void _handleSubmit() {
  if (_canSubmit) {
    viewModel.command.execute(dto);
  }
}
```

---

### Botão principal

O botão principal deve permanecer desabilitado enquanto:

* O formulário for inválido
* O Command estiver executando

```dart
ListenableBuilder(
  listenable: viewModel.command,
  builder: (_, __) {
    return ButtonSave(
      onPressed:
          viewModel.command.value.isRunning ||
                  !_canSubmit
              ? null
              : _handleSubmit,
    );
  },
)
```

---

## Listener de Command

```dart
void _commandListener() {
  final commandValue =
      viewModel.command.value;

  commandValue.onSuccess((result) {
    AppSnackBar.showSuccess(
      context,
      'Operação realizada com sucesso',
    );
  });

  commandValue.onFailure((exception) {
    AppSnackBar.showError(
      context,
      exception?.toString() ?? 'Erro',
    );
  });
}
```

---

## Estado de Loading

```dart
ListenableBuilder(
  listenable: viewModel.command,
  builder: (_, __) {
    return ButtonSave(
      onPressed:
          viewModel.command.value.isRunning
              ? null
              : _handleSubmit,
    );
  },

```

---

## Não fazer

* Regras de negócio
* HTTP
* Services
* Repositories
* StreamController
* ScaffoldMessenger direto
* Executar Commands sem validação prévia
* Habilitar ações principais quando o formulário for inválido

---

## Observação

A UI pode utilizar Validators para validar formulários.

As regras de validação devem permanecer centralizadas na camada:

```text
domain/validators/
```
